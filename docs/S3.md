# Stream a collection to Amazon S3

Use a general-purpose S3 bucket to receive evidence from multiple Windows computers.
Each collector creates a new prefix containing the hostname, UTC collection start
time and a random delivery ID. The computers can upload concurrently. An analyst
can verify a delivery directly from the bucket and optionally restore its files
under their original relative paths.

## Collect

Provision temporary AWS STS credentials through your trusted deployment system.
Kumade reads `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN`
from its process environment. The token is required on the collector. This
integration does not read AWS profiles, invoke credential helper programs or
require the AWS CLI. Give the credentials enough lifetime for the whole run.
For an EC2 role or an IAM Identity Center session, export temporary credentials
from your trusted launcher before starting Kumade.

```powershell
.\kumade.exe collect --s3 s3://example-ir-evidence/cases/IR-042/ --s3-region ap-northeast-1 --no-wizard
```

The region defaults to `AWS_REGION`, then `AWS_DEFAULT_REGION`, then
`us-east-1`. Use the bucket's region. With just `--s3`, Kumade uses hybrid
delivery. Save the printed **S3 recovery workspace**, each phase URI and its
SHA-256 in the case record.

## Hybrid collection

By default, Kumade creates a protected `kumade-recovery-<UUID>` directory
beside the executable. Run Kumade from a writable evidence drive that supports
access controls, or choose an existing directory with
`--s3-hybrid-dir E:\Evidence`. Live Windows collection requires a workspace on
a separate volume from the evidence. If Kumade is installed on the Windows
volume, specify the external directory or explicitly choose `--s3-direct`.

| Mode | What stays in the workspace | After an interruption |
|---|---|---|
| Hybrid (default) | Requested RAM, paired paging and swap files, live tables, reports and upload receipts. | Resume the original staged evidence and reuse acknowledged disk files. Unconfirmed disk files require a new acquisition. |
| Direct (`--s3-direct`) | Collection metadata. A requested DumpIt capture uses its own staging directory. | In-process multipart retries. A restarted collector starts a new acquisition. |
| Full recovery (`--s3-recovery-dir`) | The full selected collection and upload receipts. | Resume all sealed evidence even if the source is gone. |

```powershell
.\kumade.exe collect --s3 s3://example-ir-evidence/cases/IR-042/ --s3-hybrid-dir E:\Evidence --memory --dumpit E:\Tools\DumpIt --no-wizard
```

RAM and paired paging and swap files are captured first, followed by fast live state.
Ordinary files, locked NTFS artifacts and named streams go directly from the
source to create-only S3 chunks. Each acquisition worker buffers up to one
`--s3-part-mib` chunk of payload. Budget disk space for the selected volatile
captures, reports and free-space reserve. Intermediate S3 chunks are uncompressed.
After an ambiguous chunk write, such as a lost reply, Kumade resends the buffered
bytes once under a fresh create-only key. The original source is read only once.
Only a positively acknowledged key enters the file receipt. A lost reply can
leave an unreferenced object in the bucket. Access denial and checksum mismatches
are reported immediately after the SDK returns them.

Use `resume-s3` with the original prefix and printed workspace. It requires
only writer credentials and the workspace. It never reacquires a changed source.
Verify the printed phase URI and SHA-256 from the analyst workstation using
`verify-s3`.

- **Collection finished.** Check `Manifest.csv` for each disk file's status and
  `Errors.csv` for failed transfers and partial observations. A partial
  collection can still be restored. If the source read stops after returning
  bytes, `RelativeOutputPath` identifies the retained prefix under
  `_KumadePartial/<ObservationId>.partial`. The row reports `Partial`, the read
  error, and the retained length and SHA-256. A source read failure before
  the first byte, or a transfer that never confirms a required chunk, produces
  no recoverable file for that observation. Empty files read successfully are
  recorded as zero-length files.
- **Collector stopped before the final seal.** Resume publishes a partial
  `recovered-disk` phase when disk receipts or a readable plan are available.
  Restore this phase to retrieve completed files and `DiskRecovery.json`.
  `NotConfirmed` identifies a planned file without a durable complete-file
  receipt. Any reacquisition is a later observation. Chunks from an unfinished
  file may remain unreferenced in the bucket.
- Keep the workspace until the analyst has verified the relevant phases. The
  staged metadata alone does not constitute a restored disk collection.

## Recoverable phased collection

For an unreliable link or a one-time RAM capture, supply `--s3-recovery-dir` on
protected external storage. Budget enough space for the full selected collection,
RAM and pagefiles, plus the configured free-space reserve. The workspace persists
after delivery.

```powershell
.\kumade.exe collect --s3 s3://example-ir-evidence/cases/IR-042/ --s3-region ap-northeast-1 --s3-recovery-dir E:\Evidence --no-wizard
```

Add `--memory --dumpit <path-to-DumpIt.exe>` for RAM and the paired pagefile
capture. Recovery mode uses its external workspace for this capture. Record the
**S3 recovery workspace** path and each phase's URI and SHA-256 in the case log
over a trusted channel.

| Phase | What the analyst receives |
|---|---|
| `live` | Fast live datasets, including selected process, network, DNS and session information, with their original provider timestamps and inventory. |
| `memory` | The original RAM capture, paired paging and swap files when available, and provider records that document capture failures. |
| `hot-disk` | Observations and available files from the volatile disk batches, including selected USN, transaction log, MFT, event log, registry and active database artifacts. |
| `collection` | The entire sealed case with its original layout, acquisition manifest, coverage and summary. It reuses uploaded chunks from earlier phases. |

RAM acquisition runs first. Kumade captures the fast live information immediately
afterwards, then publishes that smaller phase first so analysts can inspect it
while RAM transfers. Acquisition and upload run independently. Disk acquisition
can continue during an outage while the external workspace has capacity.
Phase manifests list only sealed work. A failed acquisition remains partial.

### Resume an interrupted transfer

Use fresh temporary writer credentials if needed. Point at the **run workspace**
printed by the collector and the original bucket/prefix and endpoint. The command
reads staged evidence and upload receipts from the workspace. In hybrid mode,
those receipts identify the streamed disk files it can recover. You can resume
from another machine with the intact workspace.

```powershell
.\kumade.exe resume-s3 --workspace E:\Evidence\kumade-recovery-<UUID> --s3 s3://example-ir-evidence/cases/IR-042/
```

Kumade skips published phases and reuses positively acknowledged chunks. Each
chunk is an uncompressed, create-only S3 object. The default size is 8 MiB,
configurable with `--s3-part-mib`. A lost acknowledgement can require resending
that chunk under a fresh key. Resuming an unfinished large file can reread
the local staged file to check its hash. It never reruns DumpIt, live providers,
or disk collection. An interrupted attempt can leave unreferenced S3 objects.
Apply retention to the whole case prefix after the investigation.

After a collector process stops, resume can also recover a sealed volatile
capture or a sealed case whose upload plan had not yet been written. Exit code
`3` indicates a partial collection or a workspace with only early phases.
Evidence never captured before a process or power failure requires a new
observation with its own capture time.

### Verify a phase independently

On the analyst workstation, use the separate read role with the **phase URI
and hash printed by the collector**. Give each phase its own receipt. This works
before the full collection arrives.

```powershell
.\kumade.exe verify-s3 --s3 "<S3 memory URI>" --sha256 "<S3 memory SHA256>" --s3-region ap-northeast-1 --receipt .\memory-receipt.json --restore .\memory
```

The verifier reads every referenced chunk, checks its SHA-256, then checks the
reassembled file's size and SHA-256. A full case restore also checks the local
collection seal before publishing the restored directory. Each receipt identifies
the run, phase, and acquisition status. Keep the external workspace throughout
acquisition and until the analyst confirms the required receipts. Kumade never
deletes the recovery workspace automatically. The uploader's local
`*-published.json` records are acknowledgements, not verification receipts.

## Give each collector upload-only access

Use a dedicated writer role with a short-lived STS session per host. The following
identity or STS session policy limits a writer to HOST01 in one case. Substitute
your actual bucket, case and hostname. A session policy limits rights granted by
the role. Issue separate credentials for HOST02 with its own resource prefix.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject", "s3:AbortMultipartUpload"],
    "Resource": "arn:aws:s3:::example-ir-evidence/cases/IR-042/HOST01_*/*"
  }]
}
```

For a single acquisition slot, assign a fresh parent prefix per credential and
pass that exact prefix in `--s3`. Keep `s3:GetObject`, `s3:ListBucket`,
`s3:DeleteObject` and bucket administration off the collector. Grant the
analyst a separate role with `s3:GetObject` for the evidence prefix. The verifier
uses exact object keys, so it does not need to list the bucket. If the bucket
requires a customer-managed KMS key, provision the additional key permissions
for multipart encryption and analyst decryption.

Enforce create-only publication **at the bucket** so the restriction applies
even when someone uses the writer's credentials outside Kumade. Add a statement
like this to the bucket policy. It requires the conditional header on single
PUTs and multipart completion while permitting setup and individual part uploads.
Configure S3 Block Public Access and keep the bucket private.

```json
{
  "Sid": "DenyUnconditionalEvidenceWrites",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::example-ir-evidence/cases/*",
  "Condition": {
    "Null": {"s3:if-none-match": "true"},
    "Bool": {"s3:ObjectCreationOperation": "true"}
  }
}
```

A leaked writer credential can still upload new objects under its assigned prefix.
Kumade cannot inspect the bucket's effective IAM policy with these minimal rights.
Validate the policies with your own writer and analyst roles before deployment.
[Enforcing conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html) ·
[Temporary session policies](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)

## Verify and restore a direct delivery

On the analyst workstation, supply the read role's credentials and the two values
recorded by the collector. Use a new receipt file. Add `--restore` with a new
directory to reconstruct the collection for Juntei or other analysis tools.

```powershell
.\kumade.exe verify-s3 --s3 "<full Remote delivery URI>" --sha256 "<Delivery SHA256>" --s3-region ap-northeast-1 --receipt .\HOST01-receipt.json --restore .\HOST01
```

The verifier checks the final descriptor hash, stored and decompressed SHA-256
digests, file lengths, sealed metadata, and the correspondence between the plan,
manifest and payloads. Bulk payloads are read once from S3 without a temporary
download. The receipt distinguishes verified delivery from completeness of the
source acquisition. During restore, the verifier writes to a private temporary
directory beside the requested destination and publishes the files after all
checks pass. A failed check leaves the requested destination free for a retry
and produces no receipt. A valid but
partial acquisition produces a receipt and exit code 3. Preserve the inventories
for source timestamps, security descriptors and exported NTFS stream names.

## Direct-streaming retries, limits and costs

Select `--s3-direct` for the original upload-only workflow. It prints
**Remote delivery** and **Delivery SHA256**. Its metadata defaults to a
protected directory under the system temporary directory. Use `--s3-staging-dir`
to choose the parent. Live `--memory` also requires `--memory-staging-dir` in
this mode. With default hybrid delivery, either staging option alone selects
the single restartable workspace. For separate RAM and metadata staging
locations, select direct mode explicitly.

- Small objects use a single conditional PUT. Large objects use multipart upload,
  with SHA-256 for each part and conditional completion. The AWS SDK retries
  transient failures with backoff (at most five attempts per request). During a
  running collection the current part is replayable in memory. Already accepted
  parts and completed objects stay in S3.
- The default part size is 8 MiB of **stored**, typically compressed, bytes.
  Set `--s3-part-mib` from 5 to 256 before collection. S3 allows up to 10,000
  parts per object. At 8 MiB the limit is about 78 GiB per stored object.
  Larger parts increase memory use per active stream. Use `-T` to limit workers.
- Each observation produces a small create-only object in `checkpoints/`. It
  records what was collected or failed so an analyst can inspect progress before
  the final descriptor exists. Treat these as provisional observations. Each
  checkpoint incurs a PUT request in addition to evidence and metadata uploads.
- After retry exhaustion or permanent upload failure, keep the existing remote
  objects and available local metadata. A collector restart or expired STS
  credentials require a fresh run with a new ID. An interrupted live artifact
  must be reacquired.
- An upload-only collector cannot check which bytes were stored after a lost
  acknowledgement. A conflict on retry, an expired multipart upload ID, or an
  incomplete acknowledgement ends the run with exit code 2. Keep the source
  and the local staging directory reported by Kumade.
  - If the error includes the **expected SHA-256** of the final delivery record,
    run `verify-s3` with that hash and the **S3 delivery URI** printed at startup.
    It can confirm an intact collection even when the last response was lost.
  - If a payload, checkpoint or other earlier write was unconfirmed, the
    collector withholds the final delivery record. Reacquire under a new run ID.
- Configure an S3 lifecycle rule to abort incomplete multipart uploads after an
  appropriate interval. This also covers power loss before Kumade could abort an
  unfinished upload. Independent verification reads the evidence back and can incur
  S3 request and data transfer charges.
- S3-compatible endpoints can be selected explicitly with `--s3-endpoint`.
  They must support the conditional PUT and multipart operations used here.
  Use HTTPS. Plain HTTP is accepted only for a numeric loopback IP during testing.

[AWS multipart limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html)
