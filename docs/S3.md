# Stream a collection to Amazon S3

Use a general-purpose S3 bucket to receive evidence from multiple Windows computers.
Each collector creates a new prefix containing the hostname, UTC collection start
time and a random delivery ID. The computers can upload concurrently. An analyst
can verify a delivery directly from the bucket and optionally restore its files
under their original relative paths.

## Collect

Provision temporary AWS STS credentials through your trusted deployment system.
Kumade reads `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN`
from its process environment. The token is required on the collector. This
integration does not read AWS profiles, invoke credential helper programs or
require the AWS CLI. Give the credentials enough lifetime for the whole run.
For an EC2 role or an IAM Identity Center session, export temporary credentials
from your trusted launcher before starting Kumade.

```powershell
.\kumade.exe collect --s3 s3://example-ir-evidence/cases/IR-042/ --s3-region ap-northeast-1 --yes
```

The region defaults to `AWS_REGION`, then `AWS_DEFAULT_REGION`, then
`us-east-1`. Use the bucket's region. The collector prints **Remote delivery**
and **Delivery SHA256**. Save both to the case record over an independent channel.

Ordinary files and locked NTFS streams go straight to S3. Collection metadata
uses a protected staging directory. Set `--s3-staging-dir E:\Metadata` to select
an existing directory on external storage. RAM capture with DumpIt also requires
`--memory-staging-dir` and retains its normal RAM/pagefile staging footprint.
S3 is an alternative to local directory, SFTP, VHDX and E01 output.

## Give each collector upload-only access

Use a dedicated writer role with a short-lived STS session per host. The following
identity or STS session policy limits a writer to HOST01 in one case. Substitute
your actual bucket, case and hostname. A session policy limits rights granted by
the role. Issue separate credentials for HOST02 with its own resource prefix.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject", "s3:AbortMultipartUpload"],
    "Resource": "arn:aws:s3:::example-ir-evidence/cases/IR-042/HOST01_*/*"
  }]
}
```

For a single acquisition slot, assign a fresh parent prefix per credential and
pass that exact prefix in `--s3`. Keep `s3:GetObject`, `s3:ListBucket`,
`s3:DeleteObject` and bucket administration off the collector. Grant the
analyst a separate role with `s3:GetObject` for the evidence prefix. The verifier
uses exact object keys, so it does not need to list the bucket. If the bucket
requires a customer-managed KMS key, provision the additional key permissions
for multipart encryption and analyst decryption.

Enforce create-only publication **at the bucket** so the restriction applies
even when someone uses the writer's credentials outside Kumade. Add a statement
like this to the bucket policy. It requires the conditional header on single
PUTs and multipart completion while permitting setup and individual part uploads.
Configure S3 Block Public Access and keep the bucket private.

```json
{
  "Sid": "DenyUnconditionalEvidenceWrites",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::example-ir-evidence/cases/*",
  "Condition": {
    "Null": {"s3:if-none-match": "true"},
    "Bool": {"s3:ObjectCreationOperation": "true"}
  }
}
```

A leaked writer credential can still upload new objects under its assigned prefix.
Kumade cannot inspect the bucket's effective IAM policy with these minimal rights.
Validate the policies with your own writer and analyst roles before deployment.
[Enforcing conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html) ·
[Temporary session policies](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)

## Verify and restore

On the analyst workstation, supply the read role's credentials and the two values
recorded by the collector. Use a new receipt file. Add `--restore` with a new
directory to reconstruct the collection for Juntei or other analysis tools.

```powershell
.\kumade.exe verify-s3 --s3 "<full Remote delivery URI>" --sha256 "<Delivery SHA256>" --s3-region ap-northeast-1 --receipt .\HOST01-receipt.json --restore .\HOST01
```

The verifier checks the final descriptor hash, stored and decompressed SHA-256
digests, file lengths, sealed metadata, and the correspondence between the plan,
manifest and payloads. Bulk payloads are read once from S3 without a temporary
download. The receipt distinguishes verified delivery from completeness of the
source acquisition. A hash failure produces no success receipt. A valid but
partial acquisition produces a receipt and exit code 3. Preserve the inventories
for source timestamps, security descriptors and exported NTFS stream names.

## Retries, limits and costs

- Small objects use a single conditional PUT. Large objects use multipart upload,
  with SHA-256 for each part and conditional completion. The AWS SDK retries
  transient failures with backoff (at most five attempts per request). During a
  running collection the current part is replayable in memory. Already accepted
  parts and completed objects stay in S3.
- The default part size is 8 MiB of **stored**, typically compressed, bytes.
  Set `--s3-part-mib` from 5 to 256 before collection. S3 allows up to 10,000
  parts per object. At 8 MiB the limit is about 78 GiB per stored object.
  Larger parts increase memory use per active stream. Use `-T` to limit workers.
- Each observation produces a small create-only object in `checkpoints/`. It
  records what was collected or failed so an analyst can inspect progress before
  the final descriptor exists. Treat these as provisional observations. Each
  checkpoint incurs a PUT request in addition to evidence and metadata uploads.
- After retry exhaustion or permanent upload failure, keep the existing remote
  objects and available local metadata. A collector restart or expired STS
  credentials require a fresh run with a new ID. An interrupted live artifact
  must be reacquired. If only the final acknowledgement was lost, use the
  expected delivery name and SHA-256 in the error to check for a completed run.
- Configure an S3 lifecycle rule to abort incomplete multipart uploads after an
  appropriate interval. This also covers power loss before Kumade could abort an
  unfinished upload. Independent verification reads the evidence back and can incur
  S3 request and data transfer charges.
- S3-compatible endpoints can be selected explicitly with `--s3-endpoint`.
  They must support the conditional PUT and multipart operations used here.
  Use HTTPS. Plain HTTP is accepted only for a numeric loopback IP during testing.
